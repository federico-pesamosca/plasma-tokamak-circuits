The linearised NICE model, explained for developers

This page explains what the "linearised model" recently wrapped into this repository is, why a different set of matrices is a different model, and why this one belongs to one pulse at one time. It also answers whether the same scripts run it and what the IMAS-PDS integration needs. Section 10 adds a third model of the same code: the vertical-instability model, where the plasma can move up and down.

1. A matrix is a model

Both models in this repository are state-space models. That is a standard way to write a system whose future depends only on its present. Three ingredients:

state x
the list of numbers that fully describe the system right now. Here: electric currents, in amperes.
input u
what we can push on from outside. Here: coil voltages, in volts, set by a controller.
output y
what we want to read off. Here: either the currents themselves, or plasma quantities computed from them.

The model itself is two linear equations:

dx/dt = A x + B u   (how the currents change)
y = C x            (what we observe)

"dx/dt" means the rate of change of x, in amperes per second. A, B and C are matrices, which here means coupling tables:

MatrixSizeReads as
Astates × statesHow much each current pushes on the rate of change of every other current (and of itself). Entry A(i,j): one ampere in state j changes state i by A(i,j) amperes per second.
Bstates × inputsHow much each volt on each input pushes the currents. Entry B(i,k): one volt on input k changes state i by B(i,k) amperes per second.
Coutputs × statesWhich combination of currents gives each observable. A row of C is a recipe for one output.

Reading rules for the delivered files

Each matrix has its own one-line rule. The sizes are those of the NICE model; the circuit model follows the same rules with 116 states.

  • A (17×17, unit 1/s). Entry (i, j): how much the current j, in amperes, changes the rate of change of current i, in amperes per second. The diagonal is the self decay rate of each current (negative, or zero for a lossless loop). The off-diagonal entries are couplings: through mutual inductance, and through the plasma.
  • B (17×14, unit A/s per V). Entry (i, j): how fast current i starts to change when 1 V is applied on generator j.
  • C (9×17, unit of the observable per A). Entry (k, i): how much observable k moves per ampere of deviation of current i. The zmag row is in m/A, the Ip row in A/A.

How to read them in the files: rows are states (A, B) or outputs (C); columns are states (A, C) or inputs (B). The descriptor linear_model.json names every row and column (states, inputs, outputs), in file order.

The computer cannot step continuously in time, so the code converts the model once into a step form for the simulation step dt (MATLAB c2d, zero-order hold: the voltage is held constant during the step):

x(t + dt) = Ad x(t) + Bd u(t)

That single line is the whole simulation. Every time step is one matrix-vector product (plasmaless_timestep_forward.m: xnew = A*x + B*u). There is no other physics in the loop. Everything the model knows is in the numbers of A, B and C.

The point

Different numbers = different physics. Swapping the matrices does not tune a model; it replaces it. The code around them is just a loop that multiplies.

A note on the circuit model, for completeness. Its physics is the circuit law M dI/dt + R I = V. M is the mutual-inductance matrix: how a changing current in one conductor induces a voltage in another. It depends on the machine geometry only. R holds the resistances: zero for the superconducting coils, nonzero for VS3 and the vessel. V is the applied voltage. Rearranged, that law is exactly dx/dt = A x + B u with the A and B given in the table.

A third model, the vertical-instability model, adds a rigid plasma that can move up or down to the circuit model. Section 10 explains it.

3. Why the plasma makes it scenario- and time-specific

NICE solves the free-boundary equilibrium: given the coil and vessel currents, it finds where the plasma sits, what shape it has and how its current is distributed. The plasma reacts to the coil currents instantly (on the time scales that matter here). So "coil currents in, plasma position out" is a function, and that function is strongly non-linear: move the coils a little and the plasma may move a lot, or change shape.

Linearising means: take that non-linear relation at one working point, the equilibrium at 84.4176 s, and keep only its slope (the tangent) there. A straight line is easy to put into a matrix. But a tangent is only a good stand-in for the curve close to the point where it was taken.

What changes between scenarios and time slices, and what does not

  • Does not change: the conductor part. Mutual inductances and resistances come from the machine geometry. That is why the circuit model is valid for every pulse.
  • Changes: the plasma part. The slope depends on where the plasma is, its shape, its current and its profile. A different pulse, or a different time in the same pulse (the plasma grows, moves, Ip ramps), gives different numbers in A, B and C.
  • Exists only with plasma: the C matrix. Without a plasma there is no magnetic axis, X-point, gap or Ip to observe.

This is why one matrix set per (pulse, time) is needed, and why the matrices are an input of this code, not something it computes.

Eigenvalues and time constants

An eigenvalue of A, written λ (units 1/s), is a natural decay rate of the system: left alone, some combination of currents decays like eλt. The time constant is −1/λ, the time for that combination to shrink by a factor e ≈ 2.7. λ = 0 means a current that never decays (a superconducting loop with no resistance). A positive λ would mean growth: an unstable system.

All 17 eigenvalues of the NICE A have real part ≤ 0: the equilibrium is stable. A vertically unstable plasma would show a positive one (the vertical-instability model of section 10 has one). The code warns (plasmaless:unstable) if a delivered model ever has one.

4. Deviations and the operating point

The NICE model is a delta model: x, u and y are not absolute values but deviations from the equilibrium at the linearisation time. x = 0 does not mean "no current". It means "the currents are exactly those of the equilibrium at 84.4176 s". Likewise u = 0 means "the voltages of the equilibrium" (zero here, because an equilibrium holds its currents without drive in superconducting coils), and y = 0 means "the axis, Ip and gaps of the equilibrium".

To report absolute values the code needs the operating point: the absolute numbers that correspond to x = 0. They live in the descriptor file linear_model.json, field operating_point, in the IMAS sign convention:

  • coil currents: the provider's values with the sign flipped (for example CS3U −23248 A, CS1 +34332 A, VS3U −203.6 A, VS3L +203.6 A; see the sign frame below);
  • voltages: 0;
  • magnetic axis (6.29704, 0.596501) m, as given;
  • Ip = −15.0632 MA.

At every step the code computes du = u − op.voltage, advances x, then reports op.coil_current + x_to_coil · x for the coils and op.y + C_y · x for the observables. Only observables whose absolute value is known (from the descriptor, or from the F_INIT equilibrium when the descriptor lacks it) are written into the equilibrium IDS. The others (here the X-point, the gaps and Dist2ndSep) are not sent at all; they are still computed and kept as deviations in the MATLAB results files (variable Y).

The descriptor gives the numbers meaning. A matrix alone is just numbers. linear_model.json says what each row and column is: the state names, which state feeds which coil current (CS1U and CS1L both read state CS1; VS3U reads VS3 and VS3L reads −VS3), the generator inputs and how they combine the 14 pf_active coil voltages (input_map), the output names, the operating point, and the sign frame. It also carries the verified and unverified notes about the delivery, and metadata such as shot, provider_note and time.

Which pulse, and which sign (2026-10-14)

The provider's directory name and e-mail said pulse 105078. The delivered operating point did not fit that pulse: the provider's Ip of 15.06 MA was twice the 7.48 MA of 105078. Checked today against the DINA scenario of pulse 105073 (imas:hdf5?path=/work/projects/pds/pds-scenarios/105073/data/in, DD 4.1.1) at 84.4176 s: Ip = −15.0632 MA, the provider's value to the last digit with the opposite sign; magnetic axis (6.2996, 0.6115) m against the provider's (6.29704, 0.596501) m; and every coil current equal to the provider's within about 3 % in magnitude but with the sign flipped (CS3U −22500 A in DINA, +23248 A from the provider; VS3U −204 A against +204 A). The model is therefore the NICE equilibrium of pulse 105073 at 84.4176 s, and the provider counts every current (coils, passives, Ip) the other way round from the IMAS data. Positions, gaps and distances are not affected. The user confirmed pulse 105073 on 2026-10-14 (the provider had labelled it 105078) and the directory name was updated; the sign frame still awaits the provider's confirmation.

The sign frame: descriptor block convention

In one sentence: the provider counts currents the other way round, the wrapper counts them the IMAS way. The matrix files stay exactly as delivered. The descriptor tells the loader how to convert them, in a block called convention with three entries:

state_sign
+1 or −1: the sign of the provider's currents relative to IMAS. Here −1.
input_sign
+1 or −1: the same for the provider's voltages. Here −1, on the assumption that the generator voltages flip together with the current sense (power = V × I keeps its meaning). To be confirmed.
output_sign
one value per output: −1 for Ip (a current), +1 for the geometric outputs (positions and gaps do not change sign with the current frame).

The loader applies them once, when it reads the files: A is left unchanged; B is multiplied by input_sign / state_sign; each row of C is multiplied by state_sign / output_sign. Why these ratios: A maps currents to current rates, so flipping both sides cancels; B maps volts to current rates, so it changes by the ratio of the two frames; a row of C maps currents to one output, so it changes by the ratio of the state frame to that output's frame.

Net effect for this model: A and B are unchanged (−1 / −1 = +1), the Ip row of C is unchanged too (−1 / −1), and the geometric rows of C are negated (−1 / +1). In words: a positive IMAS current deviation moves the axis the opposite way from what the provider's row says, because the provider's "positive" is the IMAS "negative".

The provider's second answer (2026-10-14). In their frame a positive generator voltage gives a positive current (COCOS effects would have to be tested). "VS3 and −VS3" are VS3U and VS3L, driven by one generator in anti-series. The non-mirror rows 12 and 13 may be the linearised model "decorrelating" the two currents; the provider does not consider that normal and gave no fix.

Our check on the delivered B. All 11 CS/PF states respond positively to their own generator (CS3U 1.52 ... PF6 0.49 A/s per V), as the rule says. But the VS3 state responds with −3193 A/s per V of the VS3 generator and the −VS3 state with +1735. By the provider's rule the generator's positive sense is the VS3L direction, hence the map change to V(VS3L) − V(VS3U) (derived; explicit confirmation still pending).

5. Can the matrices change nature?

A new matrix set will arrive for every new pulse or time. What can change with it, and what cannot?

Same equilibrium code (NICE), another pulse or time

  • The form never changes: dx/dt = A x + B u, y = C x, continuous time, deviations from an equilibrium.
  • The numbers always change: they are the plasma tangent at a new point (section 3).
  • The dimensions and the meaning change only if the modelling choices change. That is the provider's decision, not the pulse's. The choices are: the number of passive currents (the delivered "simple" model lumps each passive structure and the vessel into one current each, 4 states; the provider also has a version with one current per node of the finite-element mesh, which would give hundreds of passive states); the set of observables (which gaps, how many, with or without the X-point or the second separatrix); the choice of inputs (generator voltages as here, coil voltages, or an explicit VS1); and the coil groupings (CS1 as one series circuit).

The descriptor absorbs all of these: state, input and output names, the coil map, the input map and the convention block. The code does not change. A new matrix set needs a new descriptor, nothing else.

Stability. At another time the equilibrium may be vertically unstable. Then A has one positive eigenvalue, the open-loop simulation (voltages held, no controller) diverges exponentially, and only a closed loop with the controller is meaningful. The wrapper only warns about it (warning id plasmaless:unstable) and does nothing else.

Another equilibrium code

In principle still a linear state-space model. In practice its nature can differ in ways the current loader does not accept without changes:

  • states that are not currents (some codes keep plasma position, Ip or flux as explicit states);
  • inputs that are coil currents instead of voltages (current-driven models have no voltage B matrix; the PDS controller sends voltages);
  • a non-zero D matrix (direct feedthrough from inputs to outputs);
  • a model already discretised at a fixed dt;
  • different units (kA, MA, kV) or sign/COCOS conventions;
  • outputs outside the vocabulary (rmag, zmag, rX, zX, Ip, gap<k>, Dist2ndSep).
AspectSame code, new pulse or timeOther code

What the wrapper requires today: continuous time; D = 0; every coil current obtainable as one state (one state per circuit, series coils sharing it); inputs expressible as linear combinations of the 14 pf_active coil voltages; outputs from the vocabulary; signs handled by the convention block; SI units. Anything else means extending the descriptor format and the loader, not the actor or the PDS workflow.

The actor's inputs and outputs (pf_active voltages in; pf_active, pf_passive, equilibrium out) are fixed by the PDS coupling, not by the model, so any model that fits the descriptor contract looks the same from outside.

6. Same scripts?

Yes. The pipeline is: load, configure, one shared model structure, one shared step function, shared drivers. Only the configure step differs.

The selection is a directory path. For the MUSCLE3 actor it is the setting linear_model_dir; for the MATLAB run scripts the environment variable PLASMALESS_LINEAR_MODEL_DIR (or the linear_model_dir variable in the script). Empty means the circuit model. The directory must hold linear_model.json and the matrix files.

Both configure functions return the same model struct: discrete A, B, C, D; coil names in machine-description order; a map from states to coil currents (x_to_coil); passive loop names and map (x_to_loop); observable names and rows (y_names, C_y); and the operating point (op, all zeros for the circuit model). For the linear model the 14 generator inputs are first mapped onto the 14 coil voltages with input_map (Bcoil = B·G), so the step function always takes coil voltages.

What depends on the pulse number?

In the code, nothing. The pulse number is metadata: the descriptor fields shot, provider_note and time, and the directory name. No branch in the code reads it. What does depend on the pulse:

  • The matrix numbers themselves: one set per pulse and time (section 3).
  • The verification against the scenario data: the operating point must be compared with the right pulse, which is how the 105078/105073 mix-up was found.
  • The PDS case the model runs with: its F_INIT must be the same pulse at the same time, here 105073 at t0 = 84.4176 s. pds-scenarios/105073 has DD4 data with long coil names such as "Central Solenoid 3U (CS3U)", which the code's coil-name rule handles, and an inverse-run directory. The first actor test used a 105073 F_INIT at 84.3176 s.

7. How the actor works, step by step

The actor is the MUSCLE3 component that wraps the model in PDS. It runs in one of three modes, chosen by two settings. Here is what it does, in order.

Start-up (all modes)

  1. It receives the F_INIT messages: the scenario's multi-time equilibrium and pf_active. The timestamp of the equilibrium message is the start time t0.
  2. It reads its settings (table at the end of this section).
  3. It reads the machine description and checks the coils against the F_INIT pf_active: same coils, same order. Otherwise it stops with an error.

Without plasma (linear_model_dir and vertical_equilibrium_uri empty, the default)

  • Build: the circuit model from the machine description (14 coils, 102 passive loops).
  • Starting state: coil currents from the F_INIT pf_active at t0; passive currents 0.
  • Each step: take the 14 coil voltages from the controller, compute the new currents, send pf_active (coil currents), pf_passive (102 loop currents) and an equilibrium that is a pure copy of the scenario's Ip and boundary geometric axis, interpolated at time t. There is no plasma in the model, so the controller sees zero Ip and position error.
  • operating_point is ignored.

With the linear model (linear_model_dir set)

  • Build: the linear model from the descriptor and the matrices. The model works in "changes from a reference state".
  • Starting state: all changes zero.
  • Each step:
    1. convert the 14 coil voltages into the provider's generator voltages (input map: VS1 gets nothing; VS3 = V(VS3L) − V(VS3U));
    2. subtract the reference voltages;
    3. compute the new changes (one matrix step);
    4. add the reference values and send: pf_active = reference coil currents + changes (CS1U = CS1L; VS3U and VS3L from their two states); pf_passive = 4 lumped currents (PS_1, PS_2, VV_1, VV_2); equilibrium = the scenario copy (as without plasma) with the model's own values written on top for every plasma quantity that has a known reference.

With the vertical model (vertical_equilibrium_uri set)

The actor loads the equilibrium at vertical_equilibrium_time (default t0) and builds the vertical-instability model from it (section 10). It works in changes from that equilibrium, like the linear model. Each step sends pf_active (14 coil currents), pf_passive (102 loop currents) and the scenario equilibrium with Ip and the current centre (current_centre.r, .z) written on top. The reference voltages come from the F_INIT pf_active at t0, so the plasma stays put until the controller changes the voltages.

The operating_point setting, in plain words

It says where the reference state comes from. descriptor means "the model's own reference": the descriptor for the linear model, the loaded equilibrium for the vertical model. The table below is written for the linear model. Whichever source is chosen, the other one fills, field by field, whatever the first one lacks.

9. PDS integration

The IMAS-PDS workflow plasmaless_controller (branch feature/plasmaless_controller, program plasmaless) needs no code change. Ports, timing and message flow are the same. What is needed:

  1. One settings line in the case overrides: plasmaless.linear_model_dir: <absolute dir>, and optionally plasmaless.operating_point: f_init.
  2. A matching case. The matrices belong to pulse 105073 at 84.4176 s, so the case window must start near there, with an initial state from a NICE inverse run of that pulse. Such a case was built and run on 2026-10-14 (below). The older case, 105084 at 136 s, does not match this matrix set.
  3. pf_passive consumers (recorder, sink) receive 4 loops instead of 102. Generic components accept that.
  4. The controller now sees a modelled Ip and magnetic axis instead of pass-through values, so its Ip loop acts. With the circuit model those loops saw constant references.
  5. The name. "plasmaless" is no longer accurate for the linear model: the actor is then a linear plasma-and-circuit response model. Renaming the PDS program or component is cosmetic and the user's call.
Same nature of inputs and outputs

As long as a linear model comes from NICE with the same descriptor format, the nature of the inputs and outputs does not change. Only the numbers, the number of states and the list of observables may differ, and the descriptor carries all of those. A linear model from another code would fit too, if it is expressed as A, B, C with named states, inputs and outputs.

10. The vertical-instability model

The repository now holds a third model. It answers one question the other two cannot: what happens when the plasma starts to move up or down?

What it is

It is the circuit model of section 2 with a plasma added. Same 14 coils, same 102 vessel loops, same order, and the same 14 coil voltages as inputs. On top of that comes one more piece of physics: the vertical force on the plasma.

  • The plasma is treated as a rigid current distribution. It keeps its shape and its current. It can only slide up or down as a whole.
  • The coil and vessel currents push on the plasma current (the Lorentz force). The model assumes this force is always balanced: the plasma instantly sits where the vertical force is zero.
  • Ip and the radial position are fixed. Only the height can change.

Moving the plasma changes the flux seen by every coil and vessel loop, so the currents react. That reaction moves the plasma further. For an ITER plasma this feedback runs away: the model has exactly one positive eigenvalue (section 3 explains eigenvalues). That eigenvalue is the vertical instability. Left alone, a small displacement grows exponentially.

Contrast with the NICE model

The NICE linearised model of section 3 describes the same 105073 state, yet none of its 17 eigenvalues is positive. One of the two models therefore misses or misplaces the instability. Why the NICE model has no positive eigenvalue is an open question for its provider (section 12).

What it is built from

Two ingredients: an equilibrium and the machine description. The equilibrium must give the plasma current density on a rectangular grid (profiles_2d). That is the "current distribution" that slides up and down.

  • Any IMAS entry and time with such a grid works. The DINA scenario entries of PDS (pds-scenarios/<shot>/data/in) qualify.
  • NICE outputs do not. They store the current only on an unstructured mesh, not on a rectangular grid.
  • Vessel currents are taken from the entry when it has the 102 loops. Otherwise the model stops, unless zero vessel currents are explicitly requested. The scenario entries have no vessel currents, so they need that explicit choice.
  • Sign of the flux. The data dictionary changed the sign convention of psi between DD3 and DD4. The code reads the entry's DD version to choose the sign, then checks it with Ampere's law: the current recomputed from psi must match the stored Ip, sign included.

How zIp becomes an IDS field

The model's output is called zIp: the plasma current times the vertical displacement, zIp = Ip0 × δz, in A m. The core mathematics is unchanged from the author's version. The conversion happens in the IMAS layer around it:

  1. At build time: the code computes the current centre of the equilibrium distribution: the current-weighted mean height zc0 and radius rc0. It divides the zIp row of the output matrix by Ip0. That row now gives metres of displacement per ampere of coil or vessel current change.
  2. At each step: zc = zc0 + displacement; Ip = Ip0 and rc = rc0 (both fixed by the model).
  3. Output: the actor writes these three numbers into the equilibrium it already sends: global_quantities.ip, global_quantities.current_centre.r and global_quantities.current_centre.z. The DD4 definition of current_centre.z is "vertical coordinate of current centre": exactly what the model computes. No field is reused as a placeholder.

In PDS

Nothing changes in the coupling: same port, same IDS type, same timing. Three more fields are filled in the equilibrium. The sinks and the recorder store and show them like any other field.

Caveat: the vertical loop is not closed

The PCS controller of the plasmaless_controller workflow reads Ip and the boundary geometric axis, not the current centre. It does not close the vertical loop either: the VS1 command is dropped, and VS3 gets only resistance times current. A PDS closed-loop run with this model will therefore drift away (growth rate 3 to 8 1/s) until a vertical-stabilisation controller is wired.

Note also that current_centre is a perfect position measurement. On the real machine the position comes from magnetic sensors and an equilibrium reconstruction. A possible later chain: synthetic magnetic measurements, then a reconstruction actor.
